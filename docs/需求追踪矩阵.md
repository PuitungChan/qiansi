## 1. 追踪链路定义

```
设计文档章节  →  用户故事(US)  →  用例(UC)  →  需求(FR/NFR/CR)  →  验收标准(AC)  →  验证方法  →  发布阶段
     ↑                                                                              ↓
     └──────────────────────── 变更影响回溯 ←──────────────────────────────────────┘
```

**正向追踪**回答：这个设计点有没有落到需求？这个需求有没有验收标准？
**反向追踪**回答：如果这条需求被砍，会影响哪些用户故事和用例？

### 字段定义

| 字段 | 说明 |
|---|---|
| 需求ID | 唯一标识，规则见 SRS §1.4 |
| 类型 | 功能 / 非功能 / 合规 |
| 优先级 | P0 必须 / P1 应该 / P2 可以 |
| 发布 | R1 垂直切片 / R2 小游戏验证版 / R3 完整版 |
| 设计来源 | 回溯到【设计】/【视觉】/【分层】的具体章节 |
| US | 关联用户故事 |
| UC | 关联用例 |
| AC | 关联验收标准 |
| 验证方法 | 该需求如何被证明"做对了" |

> 这 11 条**不是缺陷**，是"排除性/流程性需求"的正常形态。但其中两条必须被显式排期，否则会拖垮整个项目：
>
> - **CR-LIC-004**：版号周期预留 3–6 个月（补正可至 1 年）。漏排期 → R3 无法上线。
> - **CR-ADS-005**：广告的引入会改变版号路径。个人主体 + 纯广告可免版号；一旦加入内购，必须企业主体 + 版号。**这是立项第一天就要定的商业决策，不是开发后期的问题。**

### 5.2 无用例覆盖的需求（156 条）

用例只覆盖 8 条**关键流程**（55 条需求），其余 156 条没有用例。

**判定**：合理。用例的用途是**描述端到端的关键玩家路径与异常分支**，不是穷举需求。156 条中包括：

- 全部非功能需求（性能、加载、兼容性、安全）——它们的"验证"是测试与度量，不是用例
- 全部合规需求——验证方式是合规测试与外部审批
- 大量原子级功能需求（如 FR-PHY-004 张力值、FR-UI-001 丝点显示）——由验收标准直接覆盖即可

**规则**：**用例只给"有分支、有异常流、跨模块"的需求写**。纯原子需求不写用例，写测试用例。

### 5.3 孤立的验收标准

无。43 条 AC 全部至少关联 1 条需求。

### 5.4 高风险追踪点

| 风险 | 关联需求 | 说明 |
|---|---|---|
| **AC-01 是项目存续的判定点** | FR-LIV-003, UC-01 | 若自主解法率 < 60%，整个设计需重做。**必须在 R1 结束前测出** |
| AC-05 确定性 | FR-PHY-008, FR-CHL-005, NFR-REL-003 | 若确定性做不到，速通/排行榜/回放三条产品线同时崩塌。**R1 必须验证** |
| AC-22 L4 视差恒为 1.00 | FR-RND-002, FR-PHY-009 | 若 L4 速率不为 1.00，预判线开始"说谎"，可学习性归零 |
| AC-14 可访问性 | 19 条 US-14 相关需求 | 容易被整体推迟到 R3 后被砍。建议**辅助模式前移到 R2** |
| CR-* 合规（35 条） | — | 版号周期 3–6 个月（补正可至 1 年），**必须在 R2 阶段就启动**，不能等 R3 |

## 6. 变更影响回溯示例

当某条需求发生变更时，用本矩阵快速定位影响面。

**示例：若决定砍掉「凝神」（FR-ACT-007）**

| 影响面 | 内容 |
|---|---|
| 直接需求 | FR-ACT-007 删除 |
| 关联需求 | FR-CBT-010（BOSS 借力打力）失去输入可行性保障 |
| 用户故事 | US-09「四两拨千斤」无法成立 |
| 用例 | UC-03 主流程第 2 步失效，需重设计 |
| 验收标准 | AC-09 失效 |
| 设计来源 | 设计§4.3（借力打力）失去触屏可实现性 |
| **连锁后果** | 终章核心玩法崩塌 → FR-LVL-001（六章结构）需重排 |
| 决策建议 | **不可砍**。若要砍，须同时重新设计终章 BOSS |

## 7. 使用建议

1. **把 CSV 导入 Jira / TestRail**：`需求ID` 作为 Issue Key 或需求链接字段。
2. **每个 AC 建一个测试用例**，用例名直接用 AC 编号，形成自动化追溯。
3. **每次迭代评审时检查 §5.4 的五个高风险追踪点**。
4. **需求变更必须先走本矩阵**，确认影响面后再改 SRS。
5. **R1 结束时强制复盘 AC-01 与 AC-05** —— 这两个不过，后面全是沉没成本。

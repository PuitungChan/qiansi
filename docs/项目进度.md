### 2026-09 · 第 7 轮 — 设计问题澄清：主角 HP 与通关条件

**创始人提问**：「按游戏设计，主角需不需要增加血条（HP 值），通关的条件应该是什么？」
我查了设计文档 / 视觉规范 / SRS / 追踪矩阵四处，**顺手发现了 1 处矛盾 + 2 个需求缺口**。

**结论 1：主角有 HP，但绝不显示血条**（6 处文档一致：设计 §8.4、视觉规范 §219/§279/§304、
SRS 术语表、FR-UI-005）。HP 是隐藏数值——证据是 R3 辅助模式里有「**墨蚀宽容**」。
→ **D-040** 定案。

**⚠️ 发现的矛盾：墨蚀方向**
设计 §8.4 写"墨色向画面**边缘**侵蚀，到**边缘**=死亡"，而视觉规范 §219 + FR-CBT-007 + AC-25
**三处**都写"从画面边缘**向内**侵蚀，到**中心**=死亡"。**4:1，采纳后者**，
设计 §8.4 的措辞已加修订说明统一。

**结论 2：通关条件分三层**（都能从文档推出）
① 遭遇战 ≥3 条物理通路（FR-CBT-009）→ ② **单关 = 通过「门」**（FR-LVL-003 / 设计 §6.1）
→ ③ 章节 = 击败关底/BOSS（设计 §6.2）。**过关 ≠ 清空敌人。**

**⚠️ 发现的缺口 1**：SRS 里**没有任何一条需求定义"关卡完成条件"**。FR-LVL-003 只说"设一道门"，
没说"通过门即过关" → **D-041 记账待决**（创始人决定 M1 关卡流程开工前再补）。

**⚠️ 发现的缺口 2**：**主角的承伤数值完全没有定义**——附录 A 只有"玩家打敌人"的公式、
附录 B 只有敌人血量；主角 HP、墨蚀↔HP 映射、敌人对主角的伤害公式，**一个字都没有**。
而且 FR-CBT-007 本来就是 R2 → **R1 不实现主角承伤/死亡**（序章墨卒不伤人，避免污染 AC-01）。

**产出**
- `docs/DECISIONS.md`：新增 **D-040**（主角受伤口径，已决）、**D-041**（关卡完成判定，待决）
- `docs/牵丝_游戏设计方案.md` §8.4：墨蚀措辞统一为"边缘向内、到中心死亡"，加 v1.2 修订说明
- 未改任何代码——这一轮纯澄清，**M0 现状与 D-040/D-041 完全一致**（D-026 早就写了"不实现死亡流程"）

**验证了什么**
- 无代码改动；`npm test` 仍 **74 项全绿**（跑一遍确认没被误伤）

**没验证什么**
- D-040 的"墨蚀"表现**一行代码都还没有**（R2 才做）
- 主角 HP / 墨蚀映射 / 敌人伤害公式**仍是空白**，R2 实现 FR-CBT-007 前必须补上

### 2026-09 · 第 6 轮 — 实机反馈：投掷射程太短 + 文档归位

**创始人反馈**：「石头速度衰减太快，导致我基本上要贴近敌人甩出去才能砸到」

**实测（石块 20 m/s 平抛）**

| 摩擦 | 等效 μ | 减速度 | 3m | 6m | 9m | 12m | 15m |
|---|---|---|---|---|---|---|---|
| 0.4（旧） | 0.566 | **11.3 m/s²** | 18.1 | 16.2 | 14.0 | **11.3** | 7.7 |
| **0.1（新）** | 0.283 | 5.7 m/s² | 19.0 | 18.2 | 17.2 | **16.2** | 15.1 |

**根因**：**M0 没有刚体自转（D-025）⇒ 石块不能滚、只能滑**。滑动摩擦远大于滚动摩擦，
于是有效满伤害射程只有 ~9m，玩家必须贴脸投掷 → **D-039**：新增 `PROP_FRICTION = 0.1`
（等效摩擦，用低滑动摩擦近似"它会滚"），射程提到 ~15m。

**最强的证据是演示脚本自己变了**：修复前要助跑 180 tick（3 秒）才砸得到，
修复后只要 **30 tick（0.5 秒）**。

**顺带（文档归位）**：创始人把 `CHANGELOG.md` / `DECISIONS.md` 移到了 `docs/`。
根目录残留的 `DECISIONS.md` 是一个内容完全相同的副本（MD5 一致），已删除；
README 的目录树、阅读顺序、协作约定，以及各文档里的引用路径都已同步。
**此后所有文档一律放 `docs/`。**

**产出**

- `core/scene_m0.ts`、`tests/helpers.ts`：道具改用 `PROP_FRICTION`
- `tests/physics.test.ts`：新增"投掷射程回归护栏"（12m 处必须 > 15 m/s）
- `README.md`：目录结构 / 阅读顺序 / 协作约定改为「所有文档在 `docs/` 下」

### 2026-09 · 第 5 轮 — 第 2 轮实机反馈：攻击门槛与附着规则

| # | 反馈 | 核实与处理 |
|---|---|---|
| 1 | 「丝线能牵到敌人，还能把敌人拉动，这个设计是合理的吗？」 | **不合理，是我实现错了**。设计 §5 心法表写得很清楚：**「墨丝」（第四章）—— 可以附着于「无相」本体**，也就是"牵敌人"是第四章才解锁的能力。`M0Scenario` 里墨甲的 `anchorable` 误设为 `true` → **D-038** 改为 `false` |

**产出**

### 2026-09 · 第 3 轮 — 首次编辑器实机反馈：修「画面全空」

**背景**：创始人在 Cocos Creator 里装配完成并按播放，反馈**「游戏画面都没有」**。
这是 `cocos/**` 第一次真正被编译运行——也正是这一步才能暴露下面这个问题。

**根因（我的缺陷）**：运行时代码用 `new Node()` 创建的 `Graybox` / `DebugPanel` 节点，
其 `layer` 是 `Layers.Enum.DEFAULT`（`1073741824`），而 Canvas 自带相机的
`visibility` 是 `41943040`（`UI_2D | UI_3D`）——**两者不匹配，画出来的东西被相机整个剔除**。
编辑器里手工建的节点会被自动赋成 `UI_2D`，所以这个坑**只在运行时代码建节点时出现**，
而且不报任何错，只是什么都看不见。

排查方法（可复用）：直接读 `assets/scenes/M0Room.scene` 的 JSON——
Canvas 节点 `_layer` 与 Camera 组件 `_visibility` 都是明文，一比就知道。

**修复**
- `Bootstrap.buildRenderNode()` / `buildDebugLabel()`：显式 `layer = Layers.Enum.UI_2D`
- `GrayboxRenderer.drawBackground()`：自己铺一层全屏底色。原因：Canvas 相机的
  `_clearFlags` 是 `6`（只清深度、**不清颜色**），背景色其实来自那台 3D `Main Camera`；
  2D 灰盒一旦删掉它就没相机清屏。自己铺底后，画面与"场景里有没有别的相机"彻底解耦
- `Bootstrap.start()`：拆成"必需的渲染节点"与"非必需的调试面板"，调试面板用 try/catch 包住
  ——它出问题不该导致整个游戏看不见
- `Bootstrap.start()`：末尾打印 `[牵丝] QiansiBootstrap 已启动…`。
  **这行是给创始人排查用的**：看到 = 脚本编译并运行了；看不到 = 脚本压根没跑起来

**验证了什么**
- `npm test` 语法检查 27 个 `.ts` 全通过；64 项测试全绿（内核未受影响）
- 通过读 `.scene` JSON 确认创始人已正确加好 Canvas + Camera + Bootstrap 组件
  （脚本组件的 `__type__` 是 `a0b36iTTlZF46fL8+2IXKLX`，即 `Bootstrap.ts.meta` 里
  uuid `a0b36893-…` 的压缩形式）

**没验证什么**
- 修复本身**仍然无法在本机验证**（没有 Cocos Creator）——只能由创始人 `git pull` 后重跑确认

   ```
   **验证了什么**：……（写命令与结果，不要写"应该没问题"）
   **没验证什么**：……（这一节不许空着——如果没有，说明你没想清楚边界）
   **提交**：……
   ```

**为什么 §3 的「没验证什么」不许空着**：这个项目最大的风险不是"做得慢"，而是"我以为做完了"。
把边界写下来，下一次开工的人（可能还是我，但没有记忆）才知道从哪里接着验。

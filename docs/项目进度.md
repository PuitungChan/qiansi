**⚠️ 反馈 #1 里那个真 bug：整个深沟都在屏幕之外**

取景窗口的左下角一直钉在世界原点 (0,0)，而**地面顶面就在 y = 0**。于是：
可玩带贴在屏幕最下沿，**`y < 0` 的一切（整道深沟）被切在屏幕外**。
你不是"看不清沟"，是**屏幕上根本没有沟**。

修法：新增 `VIEW_ORIGIN_Y = -4.4`，可见窗口下移到 y ∈ [−4.4, 13.6]。
副作用正好：沟底落在屏幕外 ⇒ 读起来就是"掉下去就没了"，与"深沟"的语义一致。
（回归测试：`hud.test.ts` 断言地面与沟都在屏幕内。）

**⚠️ 同一次还发现第二个同族 bug：HUD 一直被画在屏幕外**

`Graphics` 画在**节点局部坐标**（画布中心为原点，y ∈ [−540, 540]），

算出来的 y ≈ 1035，落在屏幕上方之外。**你从来没有见过那四枚圆点。**
修法：新增 `uiToLocal()`，HUD 统一走它；`hud.test.ts` 有坐标往返断言守着。

### 2026-09 · 第 11 轮 — M1 批 3 交付（序章 5:00–8:00 质量差）

**范围**：设计 §7 的 5:00–8:00。设计原文：「场景给出一个 **60 质量的梁柱** 和一个

**⚠️ 我在这一段撞到一处设计文档自相矛盾，必须让创始人知道**

| 出处 | 原文 |
|---|---|
| 设计 §7 | 「玩家连梁柱 → 收丝 → **自己被拉了过去**」 |
| 设计 §2.2 | 「着地 → 等效质量 = ∞ → 拉丝时：**物体被拉向你**」 |

两者**不可能同时成立**。而 D-019 已把着地质量定为 1e6，那么 60 质量的梁柱
**会被玩家拖过来**，与 §7 正好相反 → **D-047**。

**裁定**：取设计 §2.6 自己的定性——「梁柱 / 佛像部件 40–60 ｜ **超重，主要作为锚点与移动手段**」，
所以梁柱做成**不可动的结构**（`static`），名义质量 60 保留在 `damageMass` 上。
这样"你被拉过去"自然成立（刚性约束把玩家拉向锚点，**与质量无关**），
而且顺手给了"离地"一个起点——设计 §4.2 的摆荡明确要求"**离地状态**"，
而着地质量 ∞ 的玩家本来永远无法被丝拽离地面。

**⚠️ 顺带发现一个真 bug（大物体根本连不上）**

`pickAnchorable` 原先比较的是"瞄准点到刚体**中心**"的距离，而附着容差只有 1.2m。
序章的横梁有 **16 米宽**——瞄准它的左端时离中心 8 米，**根本连不上**；
就算连上，丝线锚点取中心会让绳长瞬间变成 16.8m（上限 12m），**一连接就被猛拽**。
→ **D-048**：选择与锚点都改用"**表面最近点**"。

但**小物体仍取中心**：实测把石块锚点从中心挪到表面（差 0.5m）之后，
有效绳长变短，**甩速从 17 掉到 12.9 m/s**，把已通过 M0 验收的手感改坏了。
判据是"半尺寸是否超过附着容差"。

### 2026-09 · 第 3 轮 — 首次编辑器实机反馈：修「画面全空」

**背景**：创始人在 Cocos Creator 里装配完成并按播放，反馈**「游戏画面都没有」**。
这是 `cocos/**` 第一次真正被编译运行——也正是这一步才能暴露下面这个问题。

**根因（我的缺陷）**：运行时代码用 `new Node()` 创建的 `Graybox` / `DebugPanel` 节点，
其 `layer` 是 `Layers.Enum.DEFAULT`（`1073741824`），而 Canvas 自带相机的
`visibility` 是 `41943040`（`UI_2D | UI_3D`）——**两者不匹配，画出来的东西被相机整个剔除**。
编辑器里手工建的节点会被自动赋成 `UI_2D`，所以这个坑**只在运行时代码建节点时出现**，
而且不报任何错，只是什么都看不见。

排查方法（可复用）：直接读 `assets/scenes/M0Room.scene` 的 JSON——
Canvas 节点 `_layer` 与 Camera 组件 `_visibility` 都是明文，一比就知道。

**修复**
- `Bootstrap.buildRenderNode()` / `buildDebugLabel()`：显式 `layer = Layers.Enum.UI_2D`
- `GrayboxRenderer.drawBackground()`：自己铺一层全屏底色。原因：Canvas 相机的
  `_clearFlags` 是 `6`（只清深度、**不清颜色**），背景色其实来自那台 3D `Main Camera`；
  2D 灰盒一旦删掉它就没相机清屏。自己铺底后，画面与"场景里有没有别的相机"彻底解耦
- `Bootstrap.start()`：拆成"必需的渲染节点"与"非必需的调试面板"，调试面板用 try/catch 包住
  ——它出问题不该导致整个游戏看不见
- `Bootstrap.start()`：末尾打印 `[牵丝] QiansiBootstrap 已启动…`。
  **这行是给创始人排查用的**：看到 = 脚本编译并运行了；看不到 = 脚本压根没跑起来

**验证了什么**

  uuid `a0b36893-…` 的压缩形式）

## 7. 这个文件怎么维护

**我（AI）每次收工前必须做三件事：**

1. 更新 §0 速览的「当前阶段 / 整体进度 / 上一次做完的事 / 眼下卡在哪 / 最近更新」
2. 更新 §2 里受影响的需求状态 —— **状态变了必须同时给出证据**（哪条测试、哪次试玩、哪个提交）
3. 在 §3 追加一条工作日志，格式固定：
   ```
   ### <日期> · 第 N 轮 — <这件事叫什么>
   **产出**：……
   **关键决策与发现**：……（有决策就写进 `docs/DECISIONS.md`，这里只写摘要与链接）
   **验证了什么**：……（写命令与结果，不要写"应该没问题"）
   **没验证什么**：……（这一节不许空着——如果没有，说明你没想清楚边界）
   **提交**：……
   ```

**为什么 §3 的「没验证什么」不许空着**：这个项目最大的风险不是"做得慢"，而是"我以为做完了"。
把边界写下来，下一次开工的人（可能还是我，但没有记忆）才知道从哪里接着验。

## 0. 先划边界：我能做什么，不能做什么

这份清单的其余部分都由这一节推导出来。**你要准备的，恰好是我做不到的那部分。**

### 0.1 我能做的

| 能力 | 说明 |
|---|---|
| 写代码 | 游戏逻辑、物理系统、UI、工具链、构建脚本、自动化测试 |
| 生成矢量美术 | SVG / 程序化生成 / UI 稿 / 着色器代码（如你已看到的三张原型图） |
| 写文档 | 设计、需求、技术方案、测试用例、评审记录 |
| 研究与评审 | 竞品分析、技术选型、代码审查、架构决策 |
| 本地构建与验证 | 跑编译、跑测试、用 headless Chrome 渲染画面验证 |
| 调试与重构 | 读代码库、定位 bug、性能分析、模块重构 |

### 0.2 我不能做的 ★

| 做不到 | 后果 | 你必须准备 |
|---|---|---|
| **碰不到真机** | 手感、触屏精度、真实帧率、发热降频全部无法验证 | **一台中端安卓机 + 每周真人试玩** |
| **听不到声音** | 音频只能给规格，无法验收 | 音频资源 + 你自己听 |
| **无法召集真人** | AC-01（自主解法率）是项目成败的唯一判定点 | **10–20 个没看过设计文档的测试者** |
| **不能注册账号 / 签合同 / 申请版号 / 走支付** | 合规与商务完全在体外 | 主体资质、软著、版号 |
| **不能做商业决策** | 定价、主体类型、功能取舍 | **你的决策** |
| **画不出生产级水墨美术** | 我能给程序化的近似，但"笔意"需要人 | 画师（外包 / 自建 / 采购） |
| **不能作曲录音** | 古琴单弦的音色我描述得出来，做不出来 | 音乐人 / 音效库授权 |
| **没有跨会话记忆** | 我下次只能读到工作区文件，读不到这次对话 | **项目状态必须落到文件里** |

### 0.3 如果你只能准备三样东西

1. **一台中端安卓机**（骁龙 6 系或同级）—— 因为我碰不到，而这是唯一能验证手感的东西
2. **每周 1 小时的真人试玩** —— 手感是这个项目的全部，我一行都验证不了
3. **主体与变现路径的决定** —— 因为版号是最长的关键路径（3–6 个月，补正可至 1 年）

## 5. 真机与真人测试（硬约束）

**这是整个清单里唯一无法用钱或时间绕过的一项。**

### 5.1 节奏建议

| 阶段 | 频率 | 每次时长 | 记录什么 |
|---|---|---|---|
| R1 物理原型 | 每周 3 次 | 10 分钟 | 手感是否"顺"、哪里别扭 |
| R1 垂直切片 | 每周 1 次 | 15 分钟 | 卡在哪、哪里笑了、哪里想关掉 |
| R1 结束 | **一次** | 30 分钟 | **AC-01 测试（关键）** |
| R2 起 | 每两周 1 次 | 30 分钟 | 留存、卡关点、广告干扰度 |

### 5.2 AC-01 测试怎么做

**目标**：验证 ≥ 60% 的首次玩家，在 5 分钟遭遇战中 60 秒内自主使用石块击杀。

**要求**：
- 测试者**从未看过设计文档、SRS、任何原型图**
- 不要给任何提示，不要让他在旁边看你操作
- 记录：首次有效操作时间、是否使用石块、是否中途放弃
- **只需 10–20 人**，样本不大但足以判定

**我能提供**：测试脚本、记录表模板、埋点方案、结果分析
**我不能提供**：测试者本身

> 这一场测试决定项目是否继续。如果自主解法率 < 60%，**问题不在引导，在核心设计**——需要回到设计文档 §1 重新审视那七条决策。

### 5.3 每次试玩请记录三件事

1. **哪里卡了**（位置 + 时长）
2. **哪里手感怪**（具体动作）
3. **哪里笑了 / 想截图**（这是最有价值的数据——它说明涌现被感知到了）

第 3 条尤其重要。它直接验证 FR-NAM（命名系统）是否有效。

## 6. 协作机制

### 6.1 交付节奏

| 我提供 | 你提供 |
|---|---|
| 按里程碑的可运行构建 | 真机验证 |
| 每次交付的变更说明 | 每轮试玩的反馈 |
| 技术方案与风险评估 | 决策拍板 |
| 需求变更的影响分析 | 变更批准 |

### 6.2 变更流程

任何新需求（比如这次加广告）走：

```
提出 → 我用 RTM 做影响分析 → 你决策 → 更新 SRS + RTM + CHANGELOG → 排入发布阶段
```

**不允许跳过 RTM 的影响分析直接改代码。** 这是这份 SRS 存在的意义。

### 6.3 上下文管理

我跨会话只读工作区文件。所以：

- **重要决策必须写进 `DECISIONS.md`**，不能只在对话里说
- 每次开工前，我会先读 `docs/` 与 `DECISIONS.md` 恢复上下文
- 如果你发现我"忘了"什么，通常是因为它没被写进文件

## 8. M0：第一个交付物长什么样

**目标**：3 周，一个灰盒房间，验证三键操作是否成立。

| 项 | 内容 |
|---|---|
| **场景** | 一个 1920×1080 的灰色房间，一块石头，一只墨甲，一个玩家方块 |
| **验证什么** | ① 牵/收/断三键是否直觉 ② 甩动是否有爽感 ③ 预判线是否真的帮到玩家 |
| **不做什么** | 不做美术、不做关卡、不做叙事、不做音效、不做存档 |
| **我交付** | 可运行的构建 + 一段可回放的演示 + 调试面板 |
| **你交付** | 每周 3 次 × 10 分钟的试玩反馈 |

**M0 的判定**：如果你在第三次试玩后，**主动说出"我还想再甩一下"**——物理内核成立，进入 M1。
如果三次试玩后你觉得"能玩但没意思"——不进入 M1，回到设计文档重新审视。

## 9. 风险清单

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **AC-01 不达标** | 中 | **项目终止** | M1 结束前必须测出，早死早超生 |

| 单人 + AI 的产能上限 | 中 | 无法完成 R3 的 6 章内容 | 优先保 R1/R2，R3 视 R2 数据决定 |

## 10. 最后一句

这个项目最贵的不是代码，是**手感**。

代码我能写，文档我能写，美术我能做近似，甚至关卡我也能设计。但「甩出去的那一下爽不爽」——这件事只有在真机上、由真人、反复试，才能知道。

**所以你要准备的核心，其实只有两样：一台手机，和每周一小时。**

其余的都是可选项。
